## 🧭 **Overview**

This repository implements a **governed CI/CD pipeline** for ACME Health’s patient‑intake infrastructure. The pipeline enforces **HIPAA‑aligned controls**, validates Terraform changes using **OPA/Rego**, signs evidence using **AWS KMS**, and publishes immutable evidence bundles to an **S3 evidence vault**.

This system ensures:

- Infrastructure changes are **policy‑compliant**  
- All decisions are **cryptographically verifiable**  
- Evidence is **tamper‑proof**  
- PHI‑impacting resources are **continuously governed**

## 🔐 **Governed Workflow Summary**

1. **Terraform plan** is generated as JSON  
2. **Conftest** evaluates HIPAA Rego policies  
3. Both artifacts are **hashed (SHA‑256)**  
4. Hashes are **signed using AWS KMS SIGN_VERIFY**  
5. All four artifacts are packaged into a tarball  
6. Evidence is uploaded to an **immutable S3 vault**  
7. Merge is blocked if any policy fails  

Artifacts produced:

- `tfplan.json`  
- `tfplan.sig`  
- `conftest-results.json`  
- `conftest-results.sig`

## 🧪 **Verification Guide (Cryptographic Evidence Validation)**

### **1. Extract the evidence bundle**

```bash
tar -xzf evidence-2026xxxxTxxxxxxZ.tar.gz
```

### **2. Verify the Terraform plan signature**

```bash
openssl dgst -sha256 -verify public_key.pem \
  -signature tfplan.sig tfplan.sha256
```

### **3. Verify the Conftest results signature**

```bash
openssl dgst -sha256 -verify public_key.pem \
  -signature conftest-results.sig conftest-results.sha256
```

### **4. Expected output**

```
Verified OK
```

This proves:

- Evidence was generated by the governed pipeline  
- Evidence was not tampered with  
- Evidence is tied to the correct KMS key

## 🚨 **HIPAA Controls Violated by the Application (handler.py)**

The Lambda handler is intentionally insecure. It violates:

### **Technical Safeguards**
- **164.312(a)(1)** — No access control  
- **164.312(a)(2)(iv)** — No encryption enforcement  
- **164.312(b)** — No audit logging  
- **164.312(c)(1)** — No integrity controls  
- **164.312(d)** — No authentication  
- **164.312(e)(1)** — No transmission security validation  

### **Administrative Safeguards**
- **164.308(a)(1)(ii)(D)** — No activity review  
- **164.308(a)(5)(ii)(B)** — No malware protection  
- **164.308(a)(6)(ii)** — No incident handling  

### **Physical Safeguards**
- No retention or disposal controls  

These gaps are **intentional** and are mitigated by **infrastructure controls**, not application code.

## 🧱 **Terraform Controls Enforced by Rego Policies**

### **S3 Controls**
- SSE‑KMS required  
- TLS enforcement (`aws:SecureTransport`)  
- Versioning enabled  
- Public access blocked  
- No public ACLs or bucket policies  

### **DynamoDB Controls**
- SSE‑KMS required  
- PITR enabled  
- Deletion protection  
- Backup retention  

### **Lambda Controls**
- Must run inside a VPC  
- No public internet access  
- Logging enabled  
- KMS‑encrypted environment variables  
- IAM least privilege  

### **IAM Controls**
- No wildcard actions  
- No wildcard resources  
- No broad trust policies  

These controls **compensate** for the insecure handler.

## 🛡 **Threat Model (STRIDE)**

### **S — Spoofing**
- No authentication → attacker impersonates patients  

### **T — Tampering**
- No integrity checks → PHI can be altered  

### **R — Repudiation**
- No logs → no forensic trail  

### **I — Information Disclosure**
- PHI stored without enforced encryption  
- Attachments uploaded without SSE‑KMS  

### **D — Denial of Service**
- No throttling → attacker floods Lambda  

### **E — Elevation of Privilege**
- If IAM misconfigured, attacker escalates  

This threat model justifies the **infrastructure‑level controls** enforced by Rego.
